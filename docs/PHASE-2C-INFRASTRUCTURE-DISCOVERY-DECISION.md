The owner asked to resolve controls, freeze a complete manifest and qualify twice on the retained host. Private daemon configuration and host quota controls now have independently recorded evidence. Effective guest/inner engine configuration, trusted-only engine access and placement remain unavailable. A prospective command/configuration expectation is not an observed effective configuration.

The current [resumption prompt](PHASE-2C-RESUME-PROMPT.md) requires, before operational creation, resolving “exact effective configuration” and “inner placement/deadline/cancellation”, then freezing “a new complete source/configuration/identity-bound operational manifest before execution”. The daemon exception covers settings discovery, not guest creation. The actual guest controllers, engine configuration and nested placement cannot be read from a guest that has never been created. No supported static inspection path for all those effective facts has been established.

## Concrete proposed gate amendment

Permit a separate, prospectively source/artifact/configuration-bound **trusted infrastructure discovery profile** before the complete operational manifest. That profile may load the exact verified immutable template, create/start one mountless SBX guest and inspect its engine/configuration/controller/identity state through supported `sbx exec` interfaces. It may use only trusted inspection commands; no native agent, synthetic hostile worker, validator or credential/broker test runs during discovery. Every executable/image/source actually used must be pinned before its invocation; unresolved effective values are outputs to record, not defaults to accept. Missing or drifting executable identity still refuses.

All existing approved resource ceilings stay unchanged: 805,306,368 aggregate host memory bytes, one CPU, 128 tasks, zero swap; one 536,870,912-byte/one-vCPU guest included in the aggregate; 8,589,934,592 logical and allocated fixture disk bytes; 120-second startup per fixture; 600 seconds for two fresh fixtures including cleanup, with the final 30 seconds reserved; ordinary commands ten seconds and 65,536 bytes per stream. Independent aggregate placement and disk admission/accounting must be established prospectively before guest startup. Refuse if those bounds cannot be enforced. No automatic resizing, swap, package installation or limit increase.

Use exclusively owned synthetic HOME/state, no host workspace, host home, SSH agent, existing credential store or user configuration. Keep external networking denied and all inputs locally prepared and digest-verified. Refuse dynamic downloads and unpinned execution. No Docker or model-provider login is included. Current [Docker installation documentation](https://docs.docker.com/ai/sandboxes/install/) lists Docker sign-in as a prerequisite; this is documentation evidence, not an observed authentication refusal from the pinned create command. If the supported pinned path requires sign-in, record unavailable and stop; do not bypass authentication or import an existing session.

The complete operational manifest must still be frozen **after discovery and before any synthetic inner enforcement or native startup**. Then qualify the intended inner image and all required inner oracles twice under the original worker/validator grants and limits. Host prototype passes do not substitute for those observations. Caller/request credential authority remains a separate mandatory whole-runtime gate. No custom gateway, product launcher, adapter, paid provider request, Phase 2D, merge or release is included.

Remove only exact owned diagnostic fixtures and independently inspect cleanup. Keep the droplet and preparation artifacts at this decision and all blocked boundaries. Owner approval changes this specific ordering gate only; it does not make missing evidence pass or grant agent execution.
