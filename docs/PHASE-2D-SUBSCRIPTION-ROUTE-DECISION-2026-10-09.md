## Exact incompatibility in the current route

[Current dispatch](../src/crewshal/dispatch.py) sends native requests to a localhost custom provider, sets `requires_openai_auth` false, uses synthetic empty HOME/configuration, and gives the matching official Responses proxy a separate stdin credential. The owner selected subscription quota; this billing label does not change that transport's authentication behavior.

The pinned upstream `rust-v0.160.1` annotated tag resolves to commit `d27764b82f7118f674371e6d6e76271d9d606edb`. Its [proxy token reader](https://github.com/openai/codex/blob/d27764b82f7118f674371e6d6e76271d9d606edb/codex-rs/responses-api-proxy/src/read_api_key.rs#L208) accepts only ASCII letters, digits, hyphen and underscore, in a fixed 1024-byte buffer including the bearer prefix. JWT periods are rejected. Its [forwarder](https://github.com/openai/codex/blob/d27764b82f7118f674371e6d6e76271d9d606edb/codex-rs/responses-api-proxy/src/lib.rs#L73) reads that credential, replaces Authorization and Host, and forwards to its fixed upstream; it does not implement ChatGPT login, subscription-account selection or token lifecycle. The [proxy's own documentation](https://github.com/openai/codex/blob/d27764b82f7118f674371e6d6e76271d9d606edb/codex-rs/responses-api-proxy/README.md) specifies an API-key use case. This rejects the present proxy as a demonstrated subscription channel. It does not prove that every subscription credential has JWT format or that all subscription integrations are impossible.

Pinned [provider source](https://github.com/openai/codex/blob/d27764b82f7118f674371e6d6e76271d9d606edb/codex-rs/model-provider-info/src/lib.rs#L421) selects the ChatGPT Codex backend for native ChatGPT authentication. These are interface evidence, not actual installed CLI/account capabilities or credential separation.

[Public source evidence](qualification/phase-2d-subscription-route-source-evidence-v1-20261009.json) records whole-file hashes, exact observation ranges, tag resolution and a reproducible data-only retrieval command. ## Proposed native interface and login treatment

[Official app-server documentation](https://learn.chatgpt.com/docs/app-server) documents stdio JSONL transport, initialization, thread/turn requests, managed ChatGPT device-code login and account rate-limit readback. Its external `chatgptAuthTokens` mode is experimental and intended for a host already owning the authentication lifecycle. The same page describes the app-server command and WebSocket transport as experimental and unsupported for production workloads. This proposal is a bounded pilot assessment, with that limitation explicit; it is not a production-support claim.

Prospective native command interface: `[/opt/codex/bin/codex, app-server, --listen, stdio://]`, plus the exact pinned configuration values established during preparation. No TCP/WebSocket listener or remote Code Mode host is proposed. The manifest must enumerate every automatically started native helper and include it inside the existing worker memory/task ceiling, or refuse before the pilot. Disabled hooks, plugins, MCP, skills, extra agents, inherited instructions, login shell, telemetry, web search and request/stream retries remain mandatory and require pinned-version readback.

Use official managed device-code login through `account/login/start` with `type=chatgptDeviceCode`, in a separately approved preparation ceremony with a newly owned private home. The operator completes the official login. No ambient authentication cache, credential store or existing token is read or copied. No new custom authentication manager is proposed. Do not adopt `chatgptAuthTokens` merely to extract credentials from another application. Missing official support in the pinned version is a recorded incompatibility, not permission to upgrade or invent another channel.

The privileged preparation role owns the private login home, includes its bytes/reservation in owned storage accounting, and terminates before admitting the native worker. Its cache can be presented only through a qualified native-only view; native authentication memory and any control channel are inaccessible to code tools and the validator. The tools receive neither the home, its paths/aliases, credentials, process memory nor authenticated transport authority. A separate UID or readonly cache alone cannot protect against a file tool executed inside the native process. Qualification must exercise every enabled native file tool as well as shell descendants. If the pinned interfaces cannot maintain those distinctions, this route is **NO-GO**. Do not substitute a mount name, caller flag, secret hash or native promise for evidence.

## Finite protocol and unchanged acceptance

After the native passes unchanged stopped admission, send one `initialize` and `initialized` handshake, one frozen `thread/start`, and one `turn/start` containing only the bound requirement. Accept only responses/events linked to those retained identities; reject duplicate turns, foreign threads, unexpected server requests, mutable configuration and replay. No resume, fork, second turn, model replacement or retry is permitted. The coordinator must enforce finite message/count/byte capture without trusting event text as proof of execution or success.

The original five-second origin precedes worker creation and includes app-server startup, protocol initialization, thread creation and the whole native turn. A long login, token refresh, RPC startup or model response cannot restart or extend it. Preparation does not prestart a native worker and later assign it a fresh origin. Native refresh/recovery behavior must be observably compatible with the no-retry requirement; otherwise stop this proposed route. Preserve the one-second refusal recovery grace and independent watchdog/parent/wrapper terminal observations.

The successful pilot still requires the exact fresh synthetic repository and unchanged original dirty/Git bytes; only README may become `phase-2d-after\n`.
