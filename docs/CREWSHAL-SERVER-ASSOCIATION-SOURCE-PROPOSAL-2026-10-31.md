## Proposed mechanism

This is an unverified design, not an accepted operational mechanism.
Capture the existing Studio monitor response header through the actual request-owned SDK stream.
Bind that observation to the immutable prepared auxiliary identity.
Retain native completion IDs from the actual Studio-to-engine response inside the matching monitor record.
Expose only content-free association records through the existing owner authentication boundary.
Expose the native task's existing completion ID beside its task ID in native slot observations.
Join those identities only when a matching task is explicitly active.
Never join records through time proximity, an earlier idle slot, prompt similarity, or a self-declared identifier.

Record the engine process lifetime, binary digest, slot, native completion, and native task separately.
Retain multiple inner requests explicitly. Do not reduce them to one guessed task.
The protected route must refuse automatic recovery or replay after an uncertain submission.
An observation header supplies correlation data only. It never grants execution or profile authority.
Missing headers, unsupported routes, absent native fields, or uncertain provenance must preserve unresolved termination.
Capture monotonic request and observation intervals. Keep independent clock domains separate until a bounded relationship exists.
Do not substitute a caller's timestamp for an actual server transition time.
