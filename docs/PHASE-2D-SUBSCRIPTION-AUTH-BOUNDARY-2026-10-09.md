## Exact incompatibility and smallest decision

Pinned upstream `rust-v0.160.1` resolves to `d27764b82f7118f674371e6d6e76271d9d606edb`. In [core/src/client.rs](https://github.com/openai/codex/blob/d27764b82f7118f674371e6d6e76271d9d606edb/codex-rs/core/src/client.rs#L1655), managed authentication creates an unauthorized-recovery state around the HTTP Responses request loop. After HTTP 401, recovery succeeds and the loop submits again (raw lines 1777–1803). This is independent of ordinary `request_max_retries=0` and `stream_max_retries=0`.

In [login/src/auth/manager.rs](https://github.com/openai/codex/blob/d27764b82f7118f674371e6d6e76271d9d606edb/codex-rs/login/src/auth/manager.rs#L1985), managed recovery first reloads the same account's authentication, including the unchanged-cache case, then may refresh from the authority. Successful states permit at most two additional Responses submissions for that logical HTTP request. Ordinary auth access may also proactively refresh near expiry (raw lines 2399–2405). This is not a hard count for the whole turn, the authentication HTTP transport or all preparation/account/quota reads. A native turn can make several logical requests through its existing tool loop. Five seconds limits elapsed time, not total subscription consumption.

The inspected full configuration schema and provider configuration expose no setting to disable this managed-auth recovery. This is a bounded source finding, not a proof about every Codex version. Killing the process after observing an event cannot reliably prevent a request already being retried. External `chatgptAuthTokens` is marked unstable/internal-only/do-not-use by this pinned schema and is not an approved workaround. Do not patch vendor auth, extract ambient credentials or introduce a gateway.

**Owner decision accepted:** the owner answered “Approve only vendor authentication recovery” to the exact question in this session. Permit only the stock managed-auth refresh and HTTP 401 recovery behavior for this pilot, using HTTP-only Responses (`model_providers.openai.supports_websockets=false`) and `features.unbounded_connection_retries=false`, while ordinary request/stream retries remain zero, the coordinator still sends one task/thread/turn without replay, and every operation stays inside its original deadline and controls. The narrow exception includes proactive authentication refresh; it does not promise a per-turn refresh count or hard quota cap. Authentication cache replacement must remain bound to the admitted account; unexpected identity is a refusal. No request, task, storage, setup, qualification or deadline retry is otherwise permitted. This amends the original absolute no-retry clause and has explicit owner approval for this narrow exception only.

Approval permits continued source implementation/preparation only. It grants no installation, login, provider/model execution or non-hard quota exposure. The original unconditional no-retry route remains incompatible with this pinned managed authentication; the accepted exception does not retroactively qualify that route or historical profiles. Do not silently choose a metered fallback or claim Phase 2D is complete.

## Supported credential candidate and finite lifecycle

Managed device login can prepare an exclusively owned file cache at a private native-only `CODEX_HOME`, outside `/scratch` and every tool read root. [Storage source](https://github.com/openai/codex/blob/d27764b82f7118f674371e6d6e76271d9d606edb/codex-rs/login/src/auth/storage.rs#L154) writes `auth.json`. Mode 0600 or a readonly cache is insufficient when tools share the UID. The changed profile must use restricted reads, official sandboxed filesystem helpers and fresh tool user/PID/proc/network views. [Filesystem enforcement](https://github.com/openai/codex/blob/d27764b82f7118f674371e6d6e76271d9d606edb/codex-rs/exec-server/src/fs_sandbox.rs#L153) rejects an absent platform sandbox; actual runtime/helper identity and all tool refusals remain qualification gates. Hooks must be effectively disabled because their command runner can execute in native context. This is a supported source candidate, not observed Linux isolation.

Stock [arg0 helper setup](https://github.com/openai/codex/blob/d27764b82f7118f674371e6d6e76271d9d606edb/codex-rs/arg0/src/lib.rs) creates a random helper directory under `CODEX_HOME/tmp/arg0`; the inspected path supplies no supported relocation. Denying the whole home masks those helpers. The source profile instead grants no whole-home read root, explicitly denies `/native-auth/auth.json`, `/native-auth/config.toml` and `/native-control`, and relies on the stock sandbox adding only its current exact helper directory as a readonly root. Whole filesystem tables use proper TOML inline-table syntax to preserve periods in filenames; raw dotted CLI keys would change their meaning. Qualify the exact helper directory contents, frozen executable symlink targets, readonly mounts, aliases and absence of credential/proc/FD access. Stock arg0 loads `CODEX_HOME/.env` before configuration: the freshly owned home must exclude ambient `.env`, profiles, plugins and configuration inputs from creation. None of these effective properties follows from the source profile or mode bits.

The implemented finite sequence is initialize/initialized, config/read with startup profile provenance, account read without requested refresh, authorized quota observation, one bound thread/start, one turn/start, linked turn/completed, then close the coordinator's retained stdin writer and drain streams. `account/rateLimits/read` performs authenticated network access and cannot run as an unapproved local quota probe. Preserve nullable fields and account continuity; percentages remain shared, non-hard observations.

Stdio EOF is a supported app-server shutdown trigger, but its built-in shutdown watchdog waits 45 seconds. Keep the original external five-second watchdog. Actual process exit zero, both stream EOFs and independently empty worker roles must occur before the original deadline; turn/completed supplies none of those facts. A killed or still-running server cannot become a successful capture. Exec-only argv flags cannot be copied to app-server; use the actual pinned app-server CLI and thread fields, then qualify effective configuration/instruction exclusion.
