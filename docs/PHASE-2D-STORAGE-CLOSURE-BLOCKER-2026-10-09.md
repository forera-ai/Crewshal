## Concrete correction

The current [storage owner](../src/crewshal/linux_storage.py) previously translated `LOOP_GET_STATUS64` returning `ENXIO` into an absent loop. That observation is ambiguous: a loop can be in rundown while an open loop file still retains its backing reference. The source now raises `ValueError("owned loop final release remains unknown")`. It retains all remaining handles and prevents the later backing-unlink path, including when tests deliberately substitute a zero reference scan. Other ioctl errors still propagate. No new positive closure signal or cleanup mechanism is added.

Two existing synthetic expectations are corrected, and one deleted-open regression is added in [the storage tests](../tests/acceptance/test_phase_2d_storage.py). All three failed on the checkpoint implementation because no exception was raised. They pass after the correction. The test that previously simulated immediate successful loop disappearance now checks that successful detach transport plus ambiguous status retains the backing. Independent synthetic teardown-order tests remain in the unchanged [teardown suite](../tests/acceptance/test_phase_2d_teardown.py). No synthetic success is promoted to a real release.

## Exact incompatibility with retained loop FDs

Public upstream Linux v7.0 was resolved through its annotated tag to commit `028ef9c96e96197026887c0f092424679298aae8`. The directly fetched [loop source](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/drivers/block/loop.c#L1192) has SHA-256 `c4efa222c5b390747198070d5e0f2cbf7b3ac875b0fc127f110fa10f3a370fd7`. This is upstream source evidence, **not** identity or qualification of Ubuntu `7.0.0-38-generic`, a current target kernel or any vendor patches. Cached browser line numbers differed from direct bytes; this record uses the resolved commit and direct bytes.

`loop_clr_fd` marks autoclear; with one opener it changes the loop to rundown and returns success. `loop_get_status` rejects every state other than bound, including rundown, with `ENXIO`. Actual backing teardown occurs through `lo_release` after the last loop opener is gone. The release implementation publishes unbound before putting its backing file reference. The [file-reference source](https://github.com/torvalds/linux/blob/028ef9c96e96197026887c0f092424679298aae8/fs/file_table.c) additionally distinguishes dropping a reference from completing final file destruction. Consequently neither successful detach nor a single status read certifies final allocation release. These are source-derived conclusions, not an executed kernel experiment.

The Crewshal owner retains duplicated loop-device FDs in `LinuxPhysicalOwner.handles`; each storage-job child inherits the kept loop FDs. Duplicates of one open file share that reference: closing only a child copy does not cause final loop-file release while the observer still holds another copy. The [physical protocol](../src/crewshal/linux_teardown.py) requires loop disappearance before closing backing FDs and unlinking backing leaves. It does not close the storage owner's loop-device FDs at that transition; its final handle closure covers its own namespace/task/group handles, not those owner handles. Thus the current retained-FD protocol cannot establish the final-loop-close condition of the inspected kernel route. With additional openers, autoclear can remain bound instead; the existing flag/substitution checks already refuse that unknown state. No wait or retry resolves the ownership contradiction.

## Why the remaining mechanisms cannot fill that gap retrospectively

The existing constructor receives already-existing namespace, directory, loop and backing FDs. It checks current identity and private ring provenance; it does not establish an enforced history of every reference since creation. Binding copied backing handles authenticates those copies, not exclusive kernel ownership. The effect guard requires zero extra aliases and holders **before** the first unmount. The existing bounded proc scan correctly returns unknown for empty observations. The following missing observations therefore remain blocking:

| Reference or mutation | What current observations miss | Required evidence before any positive closure |
| --- | --- | --- |
| Taskless mount namespace | No task supplies its mountinfo; a namespace FD or bind mount can retain it | Prevented namespace export/clone or an independently retained complete namespace lifetime |
| Deleted-open or mapped file | Path deletion does not retire an open file or mapping | Actual last-reference completion; retain positive FD/maps findings |
| Socket-passed reference | An in-flight file reference need not appear as the recipient's ordinary FD | Prevented transfer or observed completion of every relevant queue lifetime |
| io_uring/AIO or deferred kernel work | Registration, requests and deferred file destruction are not ordinary task-FD inventories | Effective exclusion or independently bounded completion of the relevant kernel lifetime |
| Additional/delayed loop attachment | The supplied loop set is not a global exclusive backing-reference inventory | Prevented unowned attachments/rebinding and final completion for every owned loop |
| Concurrent mutation | Matching task/start lists and successive identity snapshots do not freeze references | Effective serialization/exclusion spanning creation, handoff, release and final readback |

Linux documents [taskless namespace retention](https://man7.org/linux/man-pages/man7/namespaces.7.html), [in-flight SCM_RIGHTS descriptors](https://man7.org/linux/man-pages/man7/unix.7.html), [registered asynchronous file resources](https://man7.org/linux/man-pages/man2/io_uring_register.2.html) and [deleted-open allocation](https://man7.org/linux/man-pages/man2/unlink.2.html). [Normal unmount](https://man7.org/linux/man-pages/man2/umount.2.html) provides a busy-target refusal; it is not a global inventory of independent cloned mount trees. Private anonymous key revocation is a separate key transition, not evidence that mounts, cached filesystem state or backing allocations have disappeared.

The accepted threat model trusts the operator/coordinator host. This assessment does not add a malicious-administrator threat. It identifies missing effective reference control within the trusted lifetime; an operator assertion of exclusivity cannot replace its required retained observations. A prospective setup that prevents reference escape might be implementable, but no such complete effective mechanism is supplied by this source. This is not a general impossibility claim about Linux, eCryptfs or every possible future profile.
