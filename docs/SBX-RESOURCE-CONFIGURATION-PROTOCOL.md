# Prospective SBX resource and configuration protocol

Date: 2026-10-02. Scope: Phase 2C only. Status: **frozen help-only assessment; operational proposal denied pending prerequisites**. This protocol resolves how resources and configuration must be accounted for. It does not accept a credential design or authorize an outer VM, worker, login or provider call.

The [machine-readable manifest](qualification/phase-2c-sbx-protocol-v1.json) preserves every grant, limit and all twenty criteria from [the original protocol](qualification/phase-2c-v1.json). It pins this document, the assessment runner, its helper and the official SBX 0.46.0 binary. Read-only help observations belong to this profile alone; no earlier subset result can be imported as a pass.

## Resource decision

The worker remains the entire native runtime and every untrusted descendant. Its memory ceiling is **134,217,728 bytes**, CPU ceiling one CPU, PID ceiling 32, deadline five seconds, probe command limit ten seconds and captured output ceiling 65,536 bytes per stream. The source and candidate grants, network denial and credential exclusion remain unchanged.

SBX 0.46.0 `create --help` advertises a minimum allocation of 512 MiB, CPU auto-sizing, a default pull policy of `always` and a shared skills default of `readonly`. These are observed help claims, not measurements of operational enforcement. Directly treating the SBX sandbox as the worker conflicts with the frozen memory ceiling. Increasing the worker to 512 MiB is rejected for this protocol.

A possible outer infrastructure grant is **536,870,912 bytes and one CPU** for one local SBX instance, with no cloud resources. It is a pending proposal, not an approved allocation. Preparation remains separately bounded by the previously recorded 2 GB download/30-minute ceiling; those limits are not a runtime memory grant. A future operational manifest must also specify and bind disk, scratch, startup deadline, total experiment deadline, template digest, daemon identity and cleanup handles before creation. Defaults cannot fill these fields silently.

The outer VM may contain trusted infrastructure only. An inner independently inspected Linux container must enforce the unchanged worker grant before any native runtime starts. Only the trusted coordinator may control the inner engine; the runtime cannot receive its socket, sudo/root authority, writable cgroup controls, parent namespaces or a capability to create another worker. SBX's documented default agent with sudo and access to its in-VM engine does not supply this arrangement by itself. Running a command with `sbx exec` does not establish it either.

The operational mapping must be demonstrated with engine inspection, kernel cgroup limits and denied attempts to change those limits or access an engine socket, plus the full malicious payload suite. Test both the native parent and detached descendants. Resource/configuration observations must agree before and after start. A helper outside the 128 MiB boundary that executes untrusted runtime code invalidates the mapping. Until that evidence exists, nested mapping is **unavailable**, not compatible.

## Configuration and credential-store prerequisite

Use an existing supported broker mechanism, not a custom gateway. macOS SBX stores secrets in the system Keychain according to [Docker's credential documentation](https://docs.docker.com/ai/sandboxes/configuration/credentials/). Empty `HOME` and `XDG_CONFIG_HOME` do not create a separate macOS credential store. Consequently this session allows only help/version commands, never daemon startup, `settings list/get/set`, login, secret import/list/set or a sandbox create/run. Some apparently observational settings commands can start the daemon, according to [Docker's settings documentation](https://docs.docker.com/ai/sandboxes/configuration/settings/).

Operational testing first needs a demonstrably separate disposable OS credential domain containing synthetic secrets only, or a supported existing broker mode that never accesses the real store. A headless Linux file fallback is documented, but is not installed, selected or qualified here. Its entire broker host must be outside the worker and contain no real secrets. A synthetic token in the operator's ordinary Keychain would still violate this session's no-host-store condition. Do not call an actual provider or sign in to satisfy the prerequisite. If login is required, record unavailable unless a prospectively approved synthetic/offline path exists.

Before starting any daemon, freeze its exact empty inherited environment, synthetic home/state/runtime directories, explicit local endpoint, global deny-all policy, pinned templates/tools and effective settings. Explicitly disable shared skills, SSH forwarding, host clipboard/file/socket access, host MCP/gateway servers, kits/mixins, environment-file lifecycle commands, dynamic secret commands, automatic credential import, OAuth passthrough and inherited global/project customizations. Empty environment is necessary but does not prove these settings are effective. Never inspect the operator's real settings to construct this profile.

The CLI help allowlist is exactly `version`, `create --help`, `daemon start --help`, `exec --help`, `secret set-custom --help` and `settings --help`. Each command runs from a fresh synthetic directory with empty inherited environment and macOS network denial, with a ten-second timeout and 65,536-byte output checks. Capture is bounded after collection and is suitable only for the pinned help binary, not hostile output. These commands deliberately perform no broker or worker operations.

## Remaining operational probes and independent oracles

Freeze a new operational manifest before these probes; fill every missing tool/image/runtime/secret-store identity and bind configuration sources. It must retain every original criterion. The following are prospective requirements, not executable commands or passing observations:

1. **Repository/global hooks:** place malicious synthetic Git and native-runtime hooks in both scopes. First prove matching positive controls execute through the actual tested startup/tool path in an isolated control fixture. Then disable the hooks in the restricted native-runtime profile and verify independent parent markers remain absent. A hook that is never reached is not a passing control. No model call may be used to reach a path in this milestone; unavailable provider-free dispatch remains unavailable.
2. **MCP/plugins/instructions:** inject synthetic repository, ancestor and global configuration, MCP/plugin registrations and instructions requesting forbidden writes and egress. Observe the actual native runtime's loaded/effective tool/configuration set; verify independent file and sink oracles. Neither ignoring files in a Python/shell payload nor documentation establishes a native-runtime pass. The whole runtime must remain inside the inspected inner grant even when instructions request broader access.
3. **Credential mediation:** keep the synthetic token outside all worker/validator mounts, files, environment, process arguments and logs. Use a local provider-shaped fixture, not an actual provider. The trusted permitted request must receive the expected synthetic header at the fixture. The worker, child and detached grandchild then attempt file/environment/proc reads, direct token replay, sentinel replay, header replacement, cross-destination requests and redirects to a second sink. Unauthorized requests must receive no authenticated service at either sink. A hidden token with unrestricted authenticated requests is a failure. Exact caller/request authorization must come from an existing tested mechanism; inventing a wrapper is not allowed.
4. **Network/native descendants:** bracket denied TCP/UDP/DNS/IPv6 attempts with positive controls; capture receipts independently at allowed and nonallowed local sinks. Cover system resolver and proxy paths, redirects and actual native-runtime/descendant authority. The prior explicit DNS-wire record cannot substitute for this evidence. Provider allowance requires a separate future approved grant; it cannot enlarge the current network-empty worker profile.
5. **Separate validator:** independent frozen candidate copy, no token, sentinel, proxy capability or provider network. Verify bytes/modes and digest before/after; test replay from the validator rather than inferring its authority from the worker's outcome.
6. **Binding/refusal:** bind OS/kernel, daemon/binary/template/image/runtime/toolchain, all configuration and manifest/payload digests, both resource layers, credential mechanism identity and exact effective grants. Reproduce from fresh fixtures twice. Changed identity, failed/unavailable/malformed/missing observations and output/terminal disagreement must refuse before native start. Do not combine independent historical subsets into a whole-runtime record.

The existing [qualification refusal API](../src/crewshal/qualification.py) remains unchanged and cannot grant execution. All seven residual whole-runtime criterion categories remain unavailable: network-egress, repository-hooks, global-hooks, mcp-plugins-instructions, credential-mediation, configuration-binding and qualification-refusal. Native conformance for earlier lifecycle/filesystem categories also remains unproved.

## Decision and next gate

The pinned SBX CLI is inspectable; direct worker sizing is incompatible with its advertised minimum. Nested resource enforcement, separate credential-store operations and caller-specific request authority have no operational evidence. SBX remains a candidate, not an accepted design. Public Orchestrate/Orka reuse decisions remain unchanged; no seam has been integrated into this unavailable boundary.

The next consequential choice is an approved disposable broker test environment plus the explicit outer allocation above, or another existing mechanism meeting the frozen worker grant. Prepare and test it prospectively; owner design acceptance follows concrete synthetic evidence. Do not approve the broker merely to convert the current record to a pass. Any failure or missing capability preserves denial. Phase 2D stays gated.
